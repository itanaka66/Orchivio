# Typed clients (FR-031)

Orchivio generates a **typed client** for the data API of an application, from its model, in **TypeScript, Python and C#**.

```bash
orchivio client model.yaml -o inventory-client.ts                     # TypeScript (default)
orchivio client model.yaml --lang python -o inventory_client.py
orchivio client model.yaml --lang csharp --namespace Acme.Stock -o InventoryClient.cs
curl -OJ -b cookies /api/v1/revisions/<revision-id>/client.ts        # or client.py, client.cs[?namespace=Acme.Stock] (needs model.read)
```

All three come from the same OpenAPI document as `orchivio openapi` (docs/MODEL-SPEC.md; `tests/integration/test_openapi.py` checks that document against real API
responses, including flow runs), so they offer the same things:

* **entity types** with the model's field types: integers, numbers, booleans, strings; enumerations as string unions (TypeScript, Python `Literal`) or strings with a
  constants class (C#); `decimal` as number-or-string; `uuid`/`date`/`date-time` as strings (the format is in the doc comment). Computed and generated fields are read-only;
* **`Create`/`Update` input types** with the model's required fields: a computed or generated field cannot be sent, a missing required field is a compile error in TypeScript and
  C# (`required` members) and a type-checker error in Python (`TypedDict`);
* **only operations at least one role may perform** (an entity nobody can delete has no delete); which role may do what stays the server's decision, its `403`/`404` come back as errors;
* **`list`** with typed `limit`, `offset`, order-by (the stored fields), `desc` and equality filters;
* **flow runs**: every server flow that has `run_roles` (and is not an entity hook) gets a method with typed arguments and a typed `FlowRunResult` (`status`, `error`,
  `error_step`, `steps_executed`, trace). Flows nobody may run directly do not appear;
* **a typed error** (`OrchivioApiError` / `OrchivioApiException`: status, code, message, details) built from the server's error envelope, also for non-JSON error pages;
* a header comment with the model hash, so a stale client can be recognised, and deterministic output.

Each file is dependency-free: TypeScript needs `fetch`; Python 3.8+ needs only the standard library (`urllib`); C# needs .NET 7+ (`required` members), `HttpClient` and
`System.Text.Json`.

```ts
const api = new OrchivioDataClient({ baseUrl: '/api/v1/applications/<id>/preview', headers: () => ({ 'X-Preview-User': 'u1', 'X-Preview-Roles': 'admin' }), credentials: 'include' })
const page = await api.product.list({ orderBy: 'name', filter: { sku: 'B-1' } })
const run = await api.flows.reorderLowStock({ min_gap: 2 })
```

```python
api = OrchivioDataClient("https://host/api/v1/applications/<id>/preview", headers=lambda: {"X-Preview-User": "u1", "X-Preview-Roles": "admin"})
made = api.product.create({"name": "Bolt", "sku": "B-1", "quantity": 3, "reorder_level": 1})
run = api.flows.reorder_low_stock({"min_gap": 2})
```

```csharp
var api = new OrchivioDataClient(http, "https://host/api/v1/applications/<id>/preview", ct => Task.FromResult<IDictionary<string, string>>(new Dictionary<string, string> { ["Authorization"] = "Bearer ..." }));
var page = await api.Product.ListAsync(new ProductListParams { OrderBy = "name", SkuEquals = "B-1" });
await api.Product.UpdateAsync(id, new Dictionary<string, object?> { ["owner"] = null });   // explicit null to clear a field
var run = await api.Flows.ReorderLowStockAsync(new ReorderLowStockArgs { MinGap = 2 });
```

In C#, `null` properties of an input object are not sent; the dictionary overload of `UpdateAsync` sends exactly what you give it, including nulls.

## How it is kept honest

* the generators are pure translations of the OpenAPI document, with a table test for every schema construct per language;
* **TypeScript**: a generated client is compiled with `tsc --strict` together with usage code, and wrong use (wrong type, missing/unknown/read-only field, unsortable field,
  wrong flow arguments) must be compile errors; the example client is checked in (`apps/web/src/generated/inventory-client.ts`), regenerated by
  `scripts/export_web_contract.py` (a drift test fails when stale) and tested with a fake `fetch`;
* **Python**: the file must parse with the Python 3.8 grammar; requests (paths, query, headers, bodies, id encoding) and every error shape are tested with a fake transport, and
  the client is run **against the real API**: create, list with filter and order, get, update, flow run, delete, 404 and 422 errors;
* **C#**: the file is **compiled with the .NET SDK with warnings as errors and executed** in a console program against a fake `HttpMessageHandler` (deserialisation, query, headers,
  bodies without nulls, explicit nulls, flow call, typed errors); a second build proves that omitting a required property does not compile. (That run found a real bug: a
  `JsonIgnore` condition that is invalid on value types.) These tests are skipped where the SDK is missing;
* the OpenAPI document itself is validated against real responses, flow runs included, for the Studio preview and the end-user API.

## Other languages

The OpenAPI 3.1 document (`orchivio openapi`, `GET /revisions/{id}/openapi.json`) is the neutral contract: use any generator (openapi-generator, Kiota, oapi-codegen, ...) for Java,
Kotlin, Go, Swift and the rest. Generators for these were not written because they could not be compiled and tested here, and an untested generator is worse than none.

## Not generated

Pages and processes (not part of the data API's OpenAPI document), authentication and token refresh (supply headers or an `HttpClient` configured for it), pagination helpers
that follow `offset` for you, retries, and a client for the platform (Studio) API, which the Studio's own `ApiClient` covers.
