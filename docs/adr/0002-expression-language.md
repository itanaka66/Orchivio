# ADR-0002: Custom CEL-inspired expression language (ADR-EXPR-001)

Status: Provisional · Date: 2026-10-17 · Resolves DESIGN.md §22 item 11 (provisionally)

## Context
One language must serve validation, computed fields, defaults, conditional UI and row-level
security. Requirements (§5.1, §8.5): static typing, null safety, purity, bounded execution,
compilation of access constraints to SQL, and low error rates when generated by an LLM.

## Decision
Implement a small custom grammar with CEL-like syntax and semantics (C-style operators,
truncating integer division, `in`, ternary, method-call style helpers) and our own type checker,
interpreter and SQL compiler (`orchivio.expr`, specified in
[EXPRESSION-SPEC.md](../EXPRESSION-SPEC.md)). Nulls are first-class and checked statically
(`??`, `?.`, no arithmetic on nullable values).

## Alternatives
- **CEL subset via an existing library.** Familiar and standard. We did **not** evaluate
  third-party CEL implementations in depth; the deciding factors were needing SQL compilation
  with null-safe semantics that match our interpreter and owning the type checker (for precise
  error positions that can be fed back to an LLM). This should be re-examined if a mature,
  embeddable implementation with a pluggable type environment is found.
- **SQL expressions directly.** Simple for row filters, unusable for client-side visibility and
  not portable to the interpreter.
- **A general scripting language.** Violates the no-arbitrary-code principle.

## Consequences
We own the grammar, so the equivalence of interpreter and SQL must be tested continuously
(`tests/unit/test_expr_sql.py`). Keeping the syntax CEL-compatible where it overlaps leaves a
migration path. An AI evaluation set for expression generation is still to be built (Phase 4/5).
